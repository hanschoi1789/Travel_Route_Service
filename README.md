# route_planner: 여행 동선 최적경로 모듈 (3번 파트)

장소 목록이 정해졌을 때 **방문 순서, 구간별 이동수단, 시간표**를 정하는 모듈입니다.
사용자 기준(시간 우선, 비용 우선 등)에 따라 결과가 달라집니다.

## 설계 요약

**목적함수 (최소화)**

```
w_time · (코스 전체 소요시간: 이동 + 대기)
+ Σ 구간 [ w_money · 요금(천원) + w_walk · 도보(km) + w_transfer · 환승수 ]
```

| 프리셋 | 의미 |
|---|---|
| fastest | 시간 최우선 (1000원 = 0.1분) |
| cheapest | 비용 최우선 (1000원 = 30분) |
| comfort | 걷기·환승 최소 (도보 1km = 20분, 환승 1회 = 10분) |
| balanced | 균형 (1000원 = 4분, 도보 1km = 3분) |

`TripRequest(weights={...})`로 가중치를 직접 지정할 수도 있습니다.

**제약조건**

| 항목 | 값 | 비고 |
|---|---|---|
| 운영시간 | 카테고리별 임의값 (`config.DEFAULT_OPEN_HOURS`) | 데이터가 생기면 `Place.open_time/close_time`에 넣으면 됨 |
| 체류시간 | 모든 장소 60~120분, 30분 단위 | 기본은 120분이고, 시간 안에 다 넣기 위해 필요할 때 알고리즘이 줄임. fastest·comfort는 체류 보존이 시간·비용보다 우선입니다. balanced는 택시와 체류 단축을 저울질하고(체류 1분 = 1.35점, 무작위 시나리오에서 택시·대중교통이 반반 나오도록 맞춘 값), cheapest는 택시를 타느니 체류를 줄입니다(30분 단축 ≈ 3,000원 가치). 프리셋의 `stay_cut` 값입니다. `Place(stay_min=..)`로 고정하거나 `min_stay`/`max_stay`로 범위 변경 |
| 식사시간 | 점심 11:00~14:30, 저녁 17:30~20:00 | 식당 체류 전체가 이 안에 들어와야 함, 식사당 식당 1곳 |
| 브레이크타임 | 15:00~17:00 | 이 시간과 식당 체류가 겹치면 안 됨 |
| 출발지·도착지, 시작·종료시각, 예산 | 사용자 입력 | 예산은 교통비 + 입장료(`Place.fee`) |
| 한 구간 최대 도보 | 1.5km | 넘으면 도보 후보에서 제외 |

**알고리즘**

1. 모든 장소 쌍 × 수단(도보, 대중교통, 택시 / 또는 자차 단독)의 이동 후보를 수집합니다 (`providers.py`).
2. 방문 순서, 식당의 점심·저녁 배정, **구간별 이동수단**을 결정합니다 (`solvers.py`).
   - `exact`(장소 8개 이하 기본): 이 셋과 **체류시간까지 동시에** 최적화하는 정확해입니다. 방문 순서를 앞에서부터 붙여 가는 깊이우선탐색으로, 부분 경로마다 (현재 시각, 누적 요금, 기타 패널티) 라벨을 들고 다니며 세 값이 모두 나쁜 라벨은 버립니다(파레토 지배). 그래서 "시간이 모자라면 이 구간만 택시", "예산이 모자라면 이 구간은 버스" 같은 판단이 시간창·예산과 함께 정확히 이뤄집니다. 무차별 대입과 비교해 25개 사례 모두 같은 답을 내고 약 100배 빠릅니다.
   - `ortools`(장소 9개 이상): 구간별 수단을 가중치로 먼저 고른 뒤 OR-Tools로 순서를 최적화합니다. 고른 수단으로 시간·예산을 못 맞추면 가중치를 조정해 다시 풀고, 그래도 안 되면 장소를 빼고 알려 줍니다.
   - `nearest`, `given`: 발표용 비교 기준입니다 (가까운 곳 먼저 / 입력 순서 그대로).
3. 해가 없으면 원인을 알려 줍니다. 어떤 수단으로도 시간이 부족한지, 아니면 시간 안에 돌려면 최소 얼마가 필요한지(정확한 최소 금액)를 보여 줍니다.

## 카카오 API 키 넣는 곳

`route_planner/config.py`의 `KAKAO_REST_API_KEY = ""`에 REST API 키를 붙여 넣으면 됩니다.
`demo.py`와 `suwon_demo.py`는 항상 카카오 API로 실제 경로를 조회합니다. 추정 모드는 없고, 키가 없으면 "카카오 REST API 키가 없습니다..." 안내 문구를 출력하고 종료합니다. 직접 짠 코드에서는 `plan(req, provider=KakaoProvider())`처럼 provider를 꼭 넘겨야 합니다.
키가 틀리거나(401) 카카오맵 사용 설정이 꺼져 있거나(403) 호출 한도를 넘으면(429) 바로 오류를 내고 멈춥니다(그때까지 받은 구간은 `kakao_cache.json`에 저장).
경로가 없거나 응답을 해석하지 못한 구간은 추정값으로 대신하지 않고 그 수단의 후보에서만 뺍니다. 실행 끝에 나오는 호출 요약에서 제외된 구간 수를 확인하세요.

## 지도 앱 (Streamlit)

```bash
pip install -r requirements.txt
streamlit run app.py
```

브라우저에서 기준별(시간 우선·비용 우선·균형) 경로를 비교할 수 있습니다.

- **기준별 비교 표:** 도착 시각, 총 소요, 비용, 택시·대중교통·도보 횟수, 환승, 체류 단축
- **한 지도에서 비교:** 기준별 경로를 색으로 구분해 겹쳐 보기. 오른쪽 위에서 켜고 끌 수 있습니다.
- **기준별 상세:** 구간마다 수단별 색(택시 주황, 지하철 파랑, 버스 초록, 도보 회색 점선)으로 그린 지도와 시간표
- **입력:** 사이드바에서 출발·도착지, 시각, 예산을 바꾸고, 장소 표를 직접 수정할 수 있습니다.
- **카카오 모드:** `config.py`에 키가 있으면 사이드바에서 "카카오 API"를 고를 수 있고, 실제 도로·노선 모양으로 그립니다.

## 사용법

```bash
pip install ortools requests
python demo.py                 # 카카오 API로 실제 경로 조회 (키 없으면 안내 후 종료)
python suwon_demo.py           # 구글 Places로 뽑은 수원 식당 2곳 + 수원화성 관광지
python benchmark.py 40         # 솔버 검증용: 무작위 40개 시나리오 (직선거리 스텁 사용, 카카오 호출 없음)
```

```python
from route_planner import Place, Location, TripRequest, KakaoProvider, plan

req = TripRequest(
    places=[Place("경복궁", 37.5796, 126.9770, "attraction"),
            Place("광장시장", 37.5701, 126.9996, "restaurant"), ...],
    origin=Location("서울역", 37.5547, 126.9707),
    destination=Location("홍대입구역", 37.5572, 126.9245),
    start_time="09:00", end_time="22:00", budget=60000, preset="balanced")
res = plan(req, provider=KakaoProvider())   # provider 필수 (추정 모드 없음)
print(res.pretty())
data = res.to_dict()       # 시각화 파트로 넘길 JSON
```

## 출력 JSON (`to_dict()`)

`stops[]`에는 장소마다 `name, lat, lng, category, meal(lunch/dinner/null), arrive, start, depart, wait_min, stay_min(실제 체류시간), stay_range([최소, 최대]), leg_in{mode, minutes, won, walk_km, transfers, distance_km, source, detail}`가 들어갑니다. 대중교통 구간의 `detail`에는 카카오 데이터일 때 세부 구간 목록이 들어갑니다. 각 항목은 `type`(SUBWAY/BUS/WALKING), `lines`(탈 수 있는 노선들), `from`/`to`(승하차 정류장), `stops`(정거장 수), `minutes`, `guidance`, `path`(지도에 그릴 [경도, 위도] 좌표)로 되어 있습니다. 이 밖에 `leg_to_destination`, `totals{duration_min, travel_min, wait_min, cost_won, walk_km, transfers, stay_min, stay_cut_min(줄인 체류시간 합), score(체류 단축 벌점 뺀 점수), objective}`, `latest_departure`(끝나는 시각을 바꾸지 않고 늦출 수 있는 출발시각), `dropped`, `warnings`가 있습니다. 예시는 `sample_output.json`에 있습니다.

## 검증 결과 (benchmark.py의 직선거리 스텁 기준)

- 정확해는 모든 순서·식사 슬롯·이동수단·체류시간 조합을 하나하나 대입한 결과와 비교해, 장소 3~5곳 사례 62개에서 모두 같은 답을 냈습니다.
- 무작위 30개 시나리오(장소 5~7곳)에서 운영시간·식사시간·브레이크타임·종료시각·예산·체류시간 범위 **위반 0건**, 정확해가 28개를 풀었습니다 (나머지 2개는 어떤 방법으로도 불가능).
- 장소 8곳(식당 2곳), 체류 기본 120분(합계 15시간)을 09~22시에 넣는 사례 8개를 모두 풀었고(체류를 약 4시간 줄여 11시간으로), 계산은 0.4~5.6초 걸렸습니다.
- 비교용 솔버(입력 순서, Nearest Neighbor, OR-Tools)는 체류시간을 모든 장소에서 똑같이 줄이는 근사 방식이라, 정확해보다 체류시간을 훨씬 많이 줄입니다. `demo.py`의 2번 비교표에서 확인할 수 있습니다.

## 한계와 다음 단계

- 카카오 provider는 문서의 응답 구조대로 작성했지만 **실제 키로는 아직 테스트하지 못했습니다.** 처음 실행할 때 응답을 한 번 확인해 주세요. 대중교통 API가 주지 않는 첫·마지막 도보 구간은 정류장 좌표로 추정합니다.
- 무료 한도(대중교통·도보 하루 1,000건)를 아끼려고 결과를 `kakao_cache.json`에 캐시하고, 멀리 떨어진 도보나 1km 미만의 대중교통은 호출 전에 거릅니다.
- 장소 9개 이상(OR-Tools)에서는 이동수단을 가중치로 미리 고르고 체류시간도 균일하게 줄이는 근사 방식이라 최적이 아닐 수 있습니다.
- 장소 빼기는 정확해(exact)에서는 허용하지 않습니다(모든 장소 필수). 장소를 빼는 건 OR-Tools 경로에서 다른 방법으로 도저히 안 될 때만 합니다.
- 시간대별 교통 변화, 여러 날 일정, 날씨는 아직 반영하지 않았습니다.
